## Findings

### H-01 — Control boundary contrast below WCAG AA

- **Where:** Pen variables `$line` / `$surface`; reusable `Field / Text input` (`jSgCJ` → `Text input control` `a0YHVh`), `Field / Select` (`bEhaY` → `Select control` `Moery`), and `Search field` (`NdxOT`).
- **Before:** each control uses `stroke: $line`, 1px; `$line` is `#E3E6EA`, `$surface` is `#FFFFFF`. Measured contrast: 1.25:1.
- **After:** choose a boundary token that reaches at least 3:1 against the control surface; remeasure after rendering.
- **Why:** a visible field boundary identifies the input/select. Current pair misses WCAG 2.2 SC 1.4.11's 3:1 non-text contrast requirement. Shared source means defect repeats across forms and search.

### M-01 — Dashboard misses its own documented dark contrast surface

- **Where:** `DESIGN.md:109,117,149`; `PG-02 Requester dashboard — Desktop` (`uL8Ys`) and mobile (`j2VAyn`).
- **Before:** dashboard uses light canvas and white panels throughout. Highest-priority “Perlu perhatian” content has no dark emphasis surface.
- **After:** apply one dark surface to the existing priority panel if it improves task hierarchy, or revise the documented direction if the screenshot-led contrast should not be retained. Do not add decorative metrics or promotional content.
- **Why:** DESIGN.md explicitly reserves one dark area as counterweight; the current rendered dashboard does not apply it. User asked to bring the current screens closer to the supplied bento reference.

### M-02 — Foundations page and visual specimens are absent

- **Where:** `design/reimburse.pen`; current component board `Requester component foundation` (`wjM1v`).
- **Before:** board shows controls, surfaces, evidence and workflow states, but no Foundation cover/index or visual samples for semantic color, typography, spacing, radius, elevation, iconography, desktop/mobile grids, and dashboard/form/detail compositions.
- **After:** add one compact Foundations section using existing Pen variables and real screen patterns. Keep reference observations separate from implementation estimates in DESIGN.md.
- **Why:** requested Foundation inventory is not yet reviewable as a coherent canvas section; current component specimens alone do not document how the system composes screens.

### M-03 — Desktop and Mobile frames are interleaved at canvas root

- **Where:** direct children of `document` in `design/reimburse.pen`; examples: dashboard desktop `uL8Ys` at root index 7, dashboard mobile `j2VAyn` at 8, list desktop `cmfPt` at 10, list mobile `UnqY7` at 11, followed by further alternating service frames. Component specimens and review states share the same root level.
- **Before:** no Desktop/Mobile role-and-flow groups; user must scan alternating screen frames among root component and review frames.
- **After:** group Foundations, Components, Desktop → Requester → flow, and Mobile → Requester → flow; label screens with shared IDs and state. Trial one frame move and verify bounds/source references before moving the remaining frames.
- **Why:** canvas organization obscures the requested device split and makes paired screen review slower.
